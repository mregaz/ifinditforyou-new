Revision 2 resolves the specific circularity identified by CGI-IR-F01. It does not infer currentness from agreement between an Authority Registry state and a matching anchor. Instead, it requires a current authenticated read from a stable logical PCTR identity whose protected revision, active-instance binding, and lifecycle state lie outside the ordinary restoration domain of the Registry and exported PCTR data.
The exact independent property that rejects A10 after A11 has been accepted is the combination of:
	•	CP1-02: protected rollback resistance;
	•	CP1-03: monotonic protected anchor revision;
	•	CP1-07: separation from the ordinary Registry/export rollback domain;
	•	CP1-01 and CP1-08: authenticated stable identity and current active access path;
	•	CP1-05: durable acceptance or explicit detectable loss.
A restored R10+A10 pair therefore cannot establish currentness merely by matching. Within the declared threat model, the protected state either remains later than A10, the restored endpoint is not recognized as active, or loss of the required protected proof produces UNPROVEN/BLOCKED.
The declared threat-model exclusion—coordinated compromise of the authenticated identity, non-regression protection, trusted technical boundary, and all independent evidence—is coherent and bounded. It does not exclude ordinary or hostile restoration of Registry data, exported anchor data, local configuration, cached endpoint metadata, DNS/configuration snapshots, retired endpoints, replays, interrupted migrations, or individual preservation-domain loss. Those attacks remain expressly in scope.
No new substantive governance authority is created. PCTR establishes technical currentness only; it cannot appoint, delegate, qualify reviewers, close findings, approve freeze, activate certification, certify, or change normative ownership.

5. CGI-IR-F01 Recheck
The defect was:
Authentic historical Registry
+
authentic, matching historical anchor
≠
demonstrably current authoritative state
Revision 1 reportedly specified comparison but did not sufficiently define how the current anchor was recognized.
Revision 2 corrects that defect by requiring:
	1	a stable logical PCTR identity;
	2	authenticated current access;
	3	a protected, non-regressing anchor revision;
	4	ordered current reads after accepted writes;
	5	an active-instance binding stored in the protected technical domain;
	6	lifecycle protection for STAGED/ACTIVE/FENCED/RETIRED;
	7	an independent rollback domain relative to ordinary Registry and exported-anchor restoration;
	8	atomic/equivalent conditional mutation;
	9	explicit fail-closed behavior where currentness evidence is uncertain;
	10	migration continuity that prevents two current instances.
The verifier does not accept an anchor because:
	•	it is signed;
	•	it has a plausible timestamp;
	•	its digest is valid;
	•	it matches the Registry;
	•	it is returned by a historically known URL;
	•	it answers a fresh challenge.
Those properties can establish authenticity, integrity, or response freshness without establishing currentness.
Currentness instead depends upon conformance of the PCTR mechanism and instance to PCTR-CP1. If that conformance or current access cannot be demonstrated, authority is UNPROVEN/BLOCKED.
CGI-IR-F01 DISPOSITION: ARCHITECTURALLY REMEDIATED

6. PCTR Architecture Recheck
PCTR is sufficiently defined as a technological class rather than a named implementation.
Its minimum state includes:
	•	PCTR_ID
	•	GOVERNANCE_EPOCH_ID
	•	LINEAGE_ID
	•	ANCHOR_REVISION
	•	REGISTRY_GENERATION
	•	REGISTRY_HEAD_DIGEST
	•	PREDECESSOR_HEAD_DIGEST
	•	OPERATION_ID
	•	STATE: CURRENT | PENDING
	•	UPDATED_AT
	•	MECHANISM_ID / PROFILE_ID
During PENDING, it also preserves the accepted predecessor and reserved successor identities.
A separate service-instance lifecycle is defined:
	•	STAGED
	•	ACTIVE
	•	FENCED
	•	RETIRED
This separation is important. A retired instance may retain an internally CURRENT historical anchor without being permitted to present itself as the current active source.
PCTR’s functions remain technical:
	•	authenticated identification;
	•	current-state reading;
	•	non-regression;
	•	ordering;
	•	conditional update;
	•	migration continuity.
PCTR does not decide what governance action should occur. It records and protects the current technical continuity state of an independently authorized transition.

11. Conditional Mutation
Revision 2 requires compare-and-set, conditional transaction, or a genuinely atomic equivalent.
Every request binds at least:
	•	active instance;
	•	epoch;
	•	lineage;
	•	expected anchor revision;
	•	expected state;
	•	operation ID;
	•	exact transition content.
For concurrent writers:
Writer A:
expected N → successor X

Writer B:
expected N → successor Y
at most one may succeed. The other must receive a precondition mismatch unless it is an identical retry of the already accepted operation.
An implementation advertising CAS while performing unprotected:
READ
→ CHECK
→ WRITE
is expressly non-conforming.
Additional determinations:
	•	Duplicate identical retry: safely recognized as idempotent.
	•	Same operation ID/different successor: rejected.
	•	Stale expected revision: rejected by conditional mutation.
	•	Operation replay: no reapplication after supersession.
	•	Cross-epoch reuse: rejected by epoch/lineage binding.
	•	Cancellation after later revision: rejected by conditional state/revision mismatch.
	•	Confirmation after supersession: rejected because confirmation binds the exact reservation and expected revision.
CONDITIONAL MUTATION: PASS

12. Revision / Generation Separation
Revision 2 correctly separates:
	•	ANCHOR_REVISION: advances on every PCTR mutation, including reservation, confirmation, cancellation, and lifecycle mutation;
	•	REGISTRY_GENERATION: advances only when a Registry successor is accepted.
The required sequence is explicitly permitted:
anchor revision 20 / registry generation 10 / CURRENT
→ anchor revision 21 / registry generation 10 / PENDING successor 11
→ anchor revision 22 / registry generation 11 / CURRENT
Cancellation creates a new anchor revision while preserving Registry generation 10. It does not return to anchor revision 20.
This prevents both counter conflation and apparent rollback through cancellation.

15. PCTR Loss / Replacement
Revision 2 distinguishes migration from loss.
Migration requires:
	•	verified current checkpoint;
	•	ordered cutover;
	•	verified cessation of the previous writer;
	•	protected continuity.
Loss means the current source is unavailable or unreliable.
A recovery may preserve lineage only if a previously adopted process retains:
	•	sufficient independent proof of the latest state; and
	•	proof that prior writers can no longer accept writes.
If either proof is absent:
BLOCKED
→ ORPHANED when no legitimate path remains
The Authority Registry cannot nominate or reconstruct its own replacement PCTR from the available copy. A new prospective epoch cannot validate the lost lineage retroactively.
This prevents the Registry from becoming its own currentness proof and prevents emergency recovery from silently creating governance authority.
PCTR LOSS / REPLACEMENT: PASS

27. Trust-Root Analysis
Revision 2’s trust root is bounded by PCTR-CP1 and the selected mechanism instance’s verified conformance.
The root assumption encompasses:
	•	stable authenticated logical identity;
	•	protected active-instance and lifecycle binding;
	•	current reads ordered after accepted writes;
	•	non-regressing protected revision;
	•	genuine conditional mutation;
	•	durable acceptance or detectable loss;
	•	rollback-domain separation;
	•	verifiable migration continuity;
	•	fail-closed behavior.
The architecture avoids infinite regress by treating these as the explicit infrastructure root assumption after conformance verification.
It avoids circularity because currentness is not derived from:
Registry says PCTR is current
or:
PCTR data say this PCTR endpoint is current
after those same data have been restored.
The active binding and protected revision must survive or detect restoration independently of the ordinary restored material. If the entire protected assumption is lost or compromised, the architecture does not manufacture a proof; it blocks or becomes orphaned.
